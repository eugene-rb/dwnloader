# Dwnloader (C# / WPF 版)

hitomi.la / momon-ga.com / pixiv.net の作品を PDF 化し、yt-dlp が対応する
サイトから動画・音声を取得する常駐ツール。URL をコピーすると自動で取り込む。

Python 版（リポジトリ直下の `app/`）を C# へ全面移植したもの。

## なぜ作り直したか

Python 版には「大量の URL を追加すると GUI が固まり、ウィンドウのドラッグも
できなくなる」という不具合があった。原因は実装方式そのものにあり、個別の
修正では消せなかった。

| Python 版 | C# 版 | 効果 |
| --- | --- | --- |
| フレームレス窓＋自前ドラッグ（120Hz のポーリングループ） | **標準の WPF ウィンドウ** | 移動・リサイズ・最大化を OS が処理する。アプリ側の負荷と競合しない |
| GIL により全スレッドが1つずつしか動けない | GIL なし。真の並列 | 裏のダウンロードや URL 解析が UI を止めない |
| pywebview の同期 `evaluate_js` で全件を JS へ送信 | `ObservableCollection` に直接束ね、一覧を仮想化 | ブリッジ自体が存在しない。画面に見えている行しか作らない |
| yt-dlp をプロセス内に import | **サブプロセス**として起動 | 重い処理も異常終了もプロセスの外。UI が巻き添えにならない |

### 実測（300 件をクリップボードから一度に投入した状態で計測）

`SendMessageTimeout` で UI スレッドが応答するまでの時間を測った。
固まっていれば、ここが伸びるか応答しなくなる。

| 項目 | 結果 |
| --- | --- |
| UI スレッドの最大応答時間 | 10.4 ms（無負荷時 9.9 ms） |
| UI が応答しなかった回数 | 0 回 / 182 回測定 |
| ウィンドウ移動 | 成功（指定どおりの位置へ動く） |
| キューへの取り込み | 300 / 300 件（取りこぼしなし） |

## 動かすのに要るもの

- Windows 10 / 11
- [.NET 8 デスクトップ ランタイム](https://dotnet.microsoft.com/download/dotnet/8.0)
- **yt-dlp**（動画・音声を取得する場合）
  `winget install yt-dlp.yt-dlp` または `pip install yt-dlp`
  実行ファイル・`python -m yt_dlp` のどちらでも自動で見つける。
  設定画面でパスを直接指定してもよい。
- **ffmpeg**（音声の取り出しと高画質動画の結合に必要）
  `winget install Gyan.FFmpeg`

画像まわり（AVIF / WebP の復号）と PDF 生成に外部ツールは要らない。
NuGet の Magick.NET と PdfSharp が実行ファイルに同梱される。

## ビルドと実行

```
cd Dwnloader
dotnet build                 # デバッグビルド
dotnet run                   # 起動

dotnet publish -c Release    # 配布用（bin/Release/net8.0-windows/publish/）
```

### 移植が正しいかを確かめる

URL 判定・ファイル名生成・日付解釈・`gg.js` 解析は、Python 版と同じ答えを
返さなければならない。ここが静かに壊れると画面を見ても気づけないため
（例: 正規表現の先頭固定の違いで hitomi の全ページが取得できなくなる）、
突き合わせ用の入口を用意してある。

```
Dwnloader.exe --selftest     # 純粋な関数の検証（101 項目）
Dwnloader.exe --dump         # Python 版と比較するための JSON を出力
Dwnloader.exe --live         # 実サーバの gg.js と実画像で、出荷する経路を通す
Dwnloader.exe --media <URL>  # yt-dlp を実際に動かして1本落とす
Dwnloader.exe --speedtest    # 速度計の計算（同時加算・上限・0への復帰）
```

`--selftest` は純粋な関数しか触らない。そこを通っただけでは、
実物の `gg.js` が読めるか・AVIF が本当に復号できるか・yt-dlp との
やり取りが成立するかは分からないので、残り3つを用意してある。

| 検証 | 何が確かめられるか |
| --- | --- |
| `--selftest` | URL 判定、ファイル名、日付、キー、`gg.js` の書式解釈、保存済みファイルからの作品特定 |
| `--dump` + Python 版の出力を diff | 移植で答えがずれていないこと（54 項目） |
| `--live` | 実サーバの `gg.js` からの画像URL組み立て、AVIF/WebP の実復号、PDF が `/DCTDecode` で無再エンコードになること |
| `--media <URL>` | yt-dlp の起動、題名・進捗の解析、保存先の受け取り |
| `--speedtest` | 速度計が実測と合うこと、複数スレッドから同時に足しても数が合うこと |

## 使い方

1. 起動するとタスクトレイに常駐し、クリップボードの監視を始める。
2. 対応サイトの URL をコピーすると自動でキューに入り、ダウンロードが始まる
   （「検出したらすぐ開始」を切れば手動開始になる）。
3. 上の入力欄に貼り付けても追加できる。複数行をまとめて貼ってよい。

- **動画 / 音声** のトグルで、これから追加するものをどちらとして保存するか決める。
  カードごとに後から切り替えることもできる（走り出す前まで）。
- **リスト全体** を切ると、再生リストやチャンネルの URL でも先頭の1本だけ取る。
- 閉じるボタンでトレイに入れる設定にできる。

## 速度のグラフ

下部バーの **速度** ボタンで、直近3分間の推移を出す。右側に現在値・最大値・
累計・進行中の件数が並ぶ。現在の速度は、グラフを畳んでいても下部バーに出る。

出すのは**全体の合計**で、1件ごとの線は引かない。数百件並ぶキューで
1本ずつ線を引いても読めないため。個別の速度は各カードに出ている。

測り方は「各ジョブが実際に受け取ったバイト数を1か所へ積み上げ、1秒ごとに
差分を取る」。ジョブが報告する瞬間の速度を足し合わせる方法だと、報告の
間隔がジョブごとに違うので合計が実測とずれる。差分なら、何本走っていても
合計は必ず実測と一致する。

グラフは畳んでいる間は描き直さない。開いていても更新は1秒に1回で、
点ごとに要素を作らず直接描いているので、表示していても操作は重くならない
（300 件を投入しながら計測して、UI の最大応答は 0.5 ms）。

## 重複の防止

同じものを二度落とさないための判定は、次の2つを見る（設定の「取得済みの作品は飛ばす」が入のとき）。

1. **履歴** — このアプリで落としたものの記録（`history.json`）
2. **実際のファイル** — 保存先と、設定で足したフォルダにあるファイル

履歴だけを見ていると、記録を消した・別の環境で落とした・手で整理した場合に
同じものをもう一度落としてしまう。実物からも判定することでそれを防ぐ。

見に行くフォルダは、**3つの保存先（PDF・動画・音声）＋設定「保存先」タブの
「重複を調べるときに追加で見るフォルダ」**。サブフォルダも辿る。過去に別の
場所へ集めた分をここに足しておけば、それも「取得済み」として扱われる。

作品の特定に使うのは、ファイル名の末尾に入る `(サイト-ID)`。保存名の
テンプレートにも yt-dlp の出力名にも同じ形で入っている。

- サイト名の綴りが違っても当たる（yt-dlp は `Youtube`、こちらは `youtube`）
- 動画と音声は拡張子で区別する。同じ動画を音声としても欲しい場合は落とせる
- `(2)` のような連番や、題名の中の括弧に惑わされない
- ID が短いとき（ギャラリーの若い番号など）はサイト名まで一致しないと同一とみなさない。
  別サイトの同じ番号を取り違えないため

走査は起動時と、保存先の設定を変えたときに裏で行う。走査中でも追加や取得は
普通にでき、その間は履歴だけで判定する。

**限界**: 判定はファイル名だけを見る。名前を変えてしまったファイルは見つけられない。
また、ファイルが多すぎる場所を指定すると途中で打ち切る（その旨をログに出す）。

## 保存先

設定・履歴・キューは `%APPDATA%\dwnloader2\` に置く。

| ファイル | 内容 |
| --- | --- |
| `settings.json` | 設定（BOM なし UTF-8。手で編集してよい）。`scan_dirs` に追加で確認するフォルダ |
| `history.json` | 取得済みの作品。「取得済みは飛ばす」の判定に使う |
| `queue.json` | 未完了のキュー。次回起動時に復元する（自動では再開しない） |
| `error.log` | 想定外の例外。通常は作られない |

Python 版とは別のフォルダを使うので、両者の設定は混ざらない。

## クリップボード監視の絞り込み

既知のサイト以外も yt-dlp の汎用抽出に賭ける（ブラックリスト式）。
ただの Web 巡回で誤検出しないよう、次の2つで絞り込む。

- **除外リスト** — このドメインは汎用抽出に回さない。取得に失敗したドメインは
  自動で追加される。
- **信頼リスト** — 除外リストより優先する。実際に取得できたドメインは自動で追加される。

ドメインは**完全一致**で比較する。サブドメインは別ドメインとして扱う
（`docs.google.com` は `google.com` に一致しない）。サブドメインごとに挙動が
違うことがあり、まとめると片方の結果が無関係な方へ波及してしまうため。

手で貼り付けた URL はこの絞り込みを受けない。

## 構成

```
Core/       モデル・設定・永続化・HTTP・URL 判定・ファイル名生成・保存済みの索引
Sites/      hitomi / momon-ga / pixiv のアダプタ
Jobs/       ダウンロード（画像・yt-dlp）、画像変換、PDF 生成、同時実行の制御
Session.cs  キューの状態とふるまい（描画は持たない）
SpeedGraph.cs  速度グラフの描画（OnRender で直接描く）
*.xaml      画面
SelfTest.cs / Compare.cs   移植の突き合わせ
```

## 注意

- ダウンロードは各サイトの利用規約と著作権法の範囲で行うこと。
- サイト側の構造が変わるとアダプタが動かなくなる。その場合はログに理由が出る。
