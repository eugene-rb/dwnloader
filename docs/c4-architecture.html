Runtime flow

代表的な URL 追加から成果物確定までの流れです。入力解決は追加順を守る直列処理、ダウンロードは種類別の並列レーンとして動作します。

URL → 完了状態失敗時は再試行可能なキュー状態を保持
01 · CAPTUREURL を受け取る

貼り付け、複数行入力、またはクリップボード監視。

02 · RESOLVESourceRef に正規化

既知サイト、専用 Resolver、汎用 Web を判定。

03 · DEDUPE重複を確認

実行中キュー、history.json、実ファイル索引を照合。

04 · SCHEDULEレーンへ投入

GalleryJob または MediaJob を同時実行枠へ。

05 · PRODUCE取得・変換

画像→JPEG→PDF、または yt-dlp→ffmpeg。

06 · COMMIT状態を確定

成果物を索引へ追加し、履歴とキューを保存。

Architecture notes

Key decisions

実装から読み取れる、システムの品質特性を支える主な設計判断です。

UI とダウンロードロジックを分離

Dwnloader.exe は WinUI 固有処理を持ち、Dwnloader.Core.dll は UI フレームワークに依存せず取得・変換ロジックを担当します。

yt-dlp を子プロセスとして隔離

重い抽出と異常終了を UI プロセスの内部状態から切り離し、中止時はプロセスツリー単位で終了します。

安全な永続化と復元

JSON は一時ファイル経由で原子的に置換し、未完了キューは次回起動時に復元します。Cookie は DPAPI で保護します。

履歴だけに頼らない重複防止

history.json と保存済みファイルの双方を照合し、履歴消失や別環境由来の成果物にも対応します。

再試行可能なギャラリーパイプライン

ページキャッシュと PDF の一時出力を使い、途中失敗で既存成果物を壊さず、取得済みページを再利用します。

適用は利用者の明示操作

更新の確認・取得と適用を分離し、実行中ジョブがある場合は再起動を伴う更新適用を避けます。
